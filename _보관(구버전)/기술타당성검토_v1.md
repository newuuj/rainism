# rainism 기술 타당성 검토 v1

> 서비스 개요(3탭: 옷장·날씨·피드)와 리서치 문서에 적힌 핵심 기능을 하나씩 뜯어서

## 0. 한 장 결론

**기술적으로는 전부 구현 가능하다. 새로 발명해야 하는 기술은 하나도 없다.**
옷 인식·배경제거·날씨 파싱·코디 추천·피드 모두 이미 상용화된 부품(비전 LLM, OS 내장 세그멘테이션, 기상청 API, 클라우드 스토리지)의 조립이다.

**진짜 병목은 "기술이 되냐"가 아니라 아래 3가지다. 전부 리서치에서 이미 예고된 것들이다.**

| 병목 | 성격 | 기술로 100% 못 푸는 이유 |
|---|---|---|
| ① AI 태깅 **품질** | 데이터 품질 | 카테고리·색은 잘 맞지만 **소재·핏은 절반 틀림**. 모델을 바꿔도 상한이 있음 → 사용자 수정(human-in-the-loop) 설계가 정답 |
| ② 옷 등록 **마찰** | UX/행동 | 기술이 아무리 싸도 "20~40벌 찍어 올리기"는 사람이 귀찮아함('12벌의 벽') |
| ③ 피드 **운영·규제** | 법/운영 | 2026.7 이미지 모더레이션 의무 강화 + 성인/불법촬영물 필터링 책임. 소셜을 켜는 순간 발생 |

→ **돈(인프라 비용)은 병목이 아니다.** 뒤에서 계산하지만 유저당 월 원가는 커피 한 잔의 수십분의 1 수준. 병목은 품질·마찰·운영이다.

## 1. 옷 등록 (사진 업로드 → 배경제거)

**"옷장에 옷을 넣는" 첫 단계. 사진 찍으면 배경을 날려 깔끔한 아이템 컷으로.**

- **무슨 기술로:** 카메라/갤러리 업로드 → **온디바이스 세그멘테이션**으로 옷만 오려냄.
  - iOS: Vision 프레임워크 `VNGenerateForegroundInstanceMaskRequest` (iOS 17+). 배경 제거가 OS에 내장.
  - Android: ML Kit **Subject Segmentation**. 전부 기기 안에서 처리, 인터넷 불필요.
- **현재 한계:**
  - 옷을 **바닥에 펼쳐/걸어서** 찍으면 잘 됨. 겹쳐 놓거나 무늬 복잡하면 경계가 지저분해질 수 있음.
  - 온디바이스라 **구형 기기에서 약간 느림/품질 차이**. 실패 시 remove.bg 같은 서버 API로 fallback.
- **남들은 어떻게:** Whering·에이클로젯도 업로드 즉시 배경 제거된 아이템 컷을 만든다(같은 방식). 에이클로젯(룩코)은 이 "디지털 옷장 만들기" 자체가 핵심 자산.
- **비용:** **온디바이스 = 사실상 0원** (기기 연산). fallback으로 remove.bg 쓰면 **장당 약 $0.20**(월 40크레딧 $9 등). → **99%를 온디바이스로 처리**하면 이 항목 비용은 무시 가능.

> ✅ 판단: 기술·비용 모두 무난. 리스크는 "촬영 가이드"(어떻게 찍게 유도하느냐)라는 UX 문제.

## 2. AI 옷 태깅 (사진 → 카테고리·색·소재·핏 자동 분류)

**옷장의 "값어치"를 결정하는 심장. 태깅이 틀리면 코디도 틀린다. (리스크 #1)**

- **무슨 기술로:** **비전 LLM**(Gemini 2.5 Flash / Claude Haiku 급)에 옷 사진 + "한글 taxonomy에 맞춰 JSON으로 뱉어" 프롬프트 → 카테고리/색/소재/핏/기장 등 구조화 출력.
- **현재 한계 (핵심):**
  - **카테고리·색 = 잘 됨.** **소재·핏 = 약 50% 오류.** 사진만으로 "린넨 vs 레이온", "슬림 vs 레귤러"를 구분하는 건 모델 한계.
  - → **해결책은 모델 교체가 아니라 UX:** 자동 태깅을 초안으로 주고, 사용자가 **탭 몇 번으로 고치게** 하는 human-in-the-loop. (리서치에서 이미 확정한 방향)
- **남들은 어떻게:** 에이클로젯·Whering 모두 자동 태깅 + 사용자 편집 병행. 완전 자동으로만 굴리는 곳은 없다 — 업계 공통으로 "사람이 마지막에 손본다".
- **비용 (오해 주의):**
  - 우리가 쓰는 건 **이미지 "이해"(입력)** 이지 **이미지 "생성"이 아니다.** (인터넷에 돌아다니는 "Gemini 이미지 $0.039/장"은 이미지를 *만드는* 값. 우리와 무관.)
  - Gemini 2.5 Flash 입력 $0.30 / 100만 토큰, 출력 $2.50 / 100만 토큰. 옷 1장 태깅 ≈ **약 $0.001~0.002**.
  - Claude Haiku 4.5 입력 $1 / 100만, 출력 $5 / 100만 → 장당 **약 $0.002~0.004**.
  - **온보딩 1회성:** 유저가 40벌 올려도 **$0.04~0.16 (약 50~200원)**. 그 뒤엔 옷 추가할 때만 발생.
  - Batch API·프롬프트 캐싱으로 최대 50~90% 추가 절감 가능.

> ✅ 판단: 비용은 껌값. **품질이 전부**다. "태깅 정확도"가 아니라 "**틀린 걸 사용자가 얼마나 쉽게 고치나**"를 KPI로 잡아야 함.

## 3. 날씨 데이터 (오늘의 체감온도·강수 "숫자" 읽기)

**앱의 트리거이자 코디 규칙의 입력값. 리서치의 코디규칙표(CSV)가 여기 붙는다.**

- **무슨 기술로:** **기상청 공공 API** (공공데이터포털 / API허브).
  - **단기예보**: 시간별 기온(TMP)·강수량(PCP)·강수형태(PTY)·강수확률(POP)·습도(REH)·최고최저(TMX/TMN).
  - CSV의 `[5] 기상청 필드 매핑` 그대로 구현: 기온→온도밴드, 습도 70%↑ +1밴드, PCP/PTY/POP→강수·우산·소재 규칙, TMX−TMN→일교차 레이어 플래그.
- **현재 한계:**
  - 전국을 **5km×5km 격자**로 제공 → 읍·면·동 단위. 초정밀은 아니지만 코디 결정엔 충분.
  - **승인에 최소 1일**, 개발계정 기본 **일 1만 콜**, 운영계정 등록 시 **일 10만 콜**까지.
  - "체감온도"는 기상청이 직접 안 주는 구간도 있어 **기온+습도+바람으로 자체 계산**(공식 존재). CSV의 습도 보정이 그 역할.
- **남들은 어떻게:** 웨디(WEDY)가 "영하 15도~영상 35도, 외출 시간대별 날씨 코디"로 이 축을 정면으로 판다. 경쟁사 공통 약점 = **"날씨 로직이 얕다"** → 우리의 CSV 규칙표가 차별화 포인트.
- **비용:** **무료.** 게다가 격자 단위라 **동네별로 캐싱**하면 유저가 1만 명이어도 실제 호출은 수백~수천 건. 사실상 0원.

> ✅ 판단: 가장 리스크 낮고 가장 차별화 쉬운 축. **원천 수치로 직접 문장 생성**(웹 날씨 스크래핑 금지)이라는 원칙도 API로 자연히 지켜짐.

## 4. AI 3코디 생성 엔진 ("랜덤 아님"을 증명하는 곳)

**핵심 가치 제안. 경쟁사 전부의 약점("추천이 랜덤 같다")을 여기서 이겨야 한다.**

- **무슨 기술로 (4단 파이프라인, 리서치 확정안):**
  1. **하드필터** — 체감온도 밴드·강수·격식으로 후보를 걸러냄 (여기서 규칙표 CSV가 작동).
  2. **소프트스코어** — 색상 3색 규칙·색 궁합·추구미 적합도로 점수화.
  3. **LLM 재랭킹** — 상위 후보를 LLM이 "오늘 맥락에 맞게" 재정렬 + 한줄 설명 생성.
  4. **MMR 다양성** — 3코디가 서로 안 겹치게(비슷한 3개 방지).
  - → **"랜덤 아님"의 80%는 1~2단(규칙·색·격식·온도)에서 나온다.** LLM은 마지막 양념.
- **현재 한계:**
  - 옷장이 **너무 적으면**(예: 12벌 미만) 조합 자체가 안 나옴 → '12벌의 벽'이 여기서도 물린다. 초기엔 "기본템 몇 개 채우기" 유도 필요.
  - LLM 재랭킹은 **설명은 잘 하지만 물리적 궁합(핏 밸런스)은 규칙이 더 정확** → LLM에 전권 주지 말 것.
- **남들은 어떻게:** 웨디·에이클로젯·Whering·Cladwell 모두 "날씨 기반 오늘의 코디"를 제공하지만, 대부분 **규칙/템플릿 위주**(Cladwell은 캡슐 옷장 템플릿, Whering은 "검증된 조합 셔플"). 우리처럼 **규칙+색스코어+LLM 재랭킹+다양성**을 명시적으로 겹쳐 쌓는 설계가 차별화.
- **비용:**
  - 규칙·스코어 단계는 **서버 연산 = 거의 0원.**
  - LLM 재랭킹만 과금: 하루 1회 3코디 기준, 옷장 텍스트+후보 넣고 ≈ 입력 2천·출력 5백 토큰 → **호출당 약 $0.002**. 매일 쓰는 유저라도 **월 $0.06 안팎(약 80원).**
  - 규칙만으로도 3코디가 나오므로, LLM 재랭킹을 **"신뢰도 낮을 때만" 조건부 호출**하면 더 내려감.

> ✅ 판단: 기술·비용 모두 OK. 승부처는 "규칙표를 얼마나 촘촘히 만드냐"(= 코드가 아니라 **기획 자산**). CSV가 그 시작.

## 5. 피드 / 소셜 (OOTD 공유 + 기온·강수 자동 태그)

**빌드 순서상 마지막. 그리고 리스크가 가장 급증하는 구간. (리스크 #3)**

- **무슨 기술로:**
  - 이미지 업로드·저장·배포 = 클라우드 스토리지 + CDN.
  - "그날 기온·강수 자동 태그" = 업로드 시점 기상청 데이터 스냅샷을 메타로 붙임(기술적으로 쉬움).
  - **콘텐츠 모더레이션**(부적절 이미지 자동 거르기) = 별도 필수.
- **현재 한계 = 대부분 법/운영 리스크:**
  - **2026.7.1** 전기통신사업법 개정 → 기존 **동영상**에만 있던 사전 필터링 의무가 **모든 이미지**로 확대(불법촬영물 대상, "AI DNA 필터링" 서버 탑재).
  - **2026.7.7** 정보통신망법(허위조작정보) → **일 활성 100만↑ 대형 플랫폼**에 자율규제 의무. 초기 스타트업은 규모 미달이지만, **성장하면 걸린다**는 걸 설계에 미리 반영.
  - 즉 소셜을 켜는 순간 **성인/불법촬영물 모더레이션은 규모와 무관하게 기본값**으로 깔아야 함.
- **남들은 어떻게:** Whering이 "소셜 옷장" 지향. 무신사 스냅 등 강자가 이미 OOTD 소셜을 점유 → **콜드스타트 + 강자 + 규제**가 겹치는 가장 어려운 판.
- **비용:**
  - **이미지 저장/배포:** Cloudflare R2 기준 저장 $0.015/GB + **전송(egress) 무료**. 유저 1만 명이 40벌+OOTD로 ~80GB 써도 **월 약 $1~2.** (S3는 전송비 때문에 훨씬 비쌈 → R2류 권장.)
  - **모더레이션:** AWS Rekognition 콘텐츠 모더레이션 **장당 $0.001**(첫 100만장), 월 5천장 무료 12개월. 업로드 1만 장/월이면 **약 $10.** Hive는 정확도 높지만 견적제(비공개).

> ⚠️ 판단: **기술·인프라 비용은 싸다. 리스크는 전부 "운영/법"이다.** → **소셜은 반드시 마지막**, 그리고 켤 때 모더레이션 파이프라인을 처음부터 함께 켤 것.

## 6. 인프라 총비용 시뮬레이션 (유저 1만 명 가정)

**"돈이 병목이 아니다"를 숫자로.**

| 항목 | 단가 | 월 규모 가정 | 월 비용(추정) |
|---|---|---|---|
| 옷 태깅(비전 LLM) | ~$0.0015/장 | 신규·추가 5만 장 | **~$75** |
| 배경제거 | 온디바이스 0원 (fallback만 과금) | 대부분 0 | **~$0** |
| 날씨(기상청) | 무료 | 캐싱 | **$0** |
| 코디 LLM 재랭킹 | ~$0.002/회 | 하루 활성 3천 명×30일 | **~$180** |
| 이미지 저장·배포(R2) | $0.015/GB, egress 0 | ~80GB | **~$1~2** |
| 피드 모더레이션 | $0.001/장 | 1만 장 | **~$10** |
| **합계** | | | **월 약 $270 (≈ 36만 원)** |

- 유저 1만 명당 **월 약 36만 원 = 유저 1인당 월 약 36원.** 커피 한 잔(약 4,500원)의 **1/125.**
- LLM 재랭킹을 조건부 호출로 줄이면 더 내려감. **인프라 원가는 사업 성패 변수가 아니다.**
- 진짜 돈 나가는 곳은 **인건비(태깅 taxonomy·규칙표·모더레이션 운영)** 와 **마케팅(콜드스타트 극복)**. → 기술비가 아니라 **사람·유통 비용**.

| 2026.7.7 | 정보통신망법(허위조작정보) | 일 활성 100만↑ 시 자율규제 의무 | 초기 규모 미달이나, **자율정책 문서·신고/조치 절차** 미리 설계 |
| 2026.1 | AI기본법 시행 | AI 자동 결정(코디·태깅) 투명성 | "왜 이 코디인지" 설명 제공(이미 LLM 한줄설명으로 충족 방향) |

> 스크래핑 금지(핀터레스트·웹 패션이미지), 콘텐츠는 **유저 업로드 또는 라이선스 어필리에이트만** — 이 원칙이 저작권·약관 리스크를 원천 차단. 이미 확정된 방향과 일치.

## 8. 최종 권고

1. **빌드 순서 유지: 옷장 → 날씨 → 피드.** 기술 난이도가 아니라 **리스크 순서**로도 정확하다(품질→차별화→운영/법).
2. **MVP에서 LLM을 최소화해도 된다.** 태깅은 비전 LLM 필요하지만, 코디는 **규칙+색스코어만으로도 3코디가 나온다**. LLM 재랭킹은 "있으면 좋은" 2차 레이어 → 비용·복잡도 낮추려면 후순위.
3. **KPI를 "정확도"가 아니라 "수정 편의성/등록 완주율"로.** ①은 human-in-the-loop UX, ②는 온보딩 마찰이 승부.
4. **소셜은 모더레이션 파이프라인과 세트로만 출시.** 따로 못 켠다.
5. **검증은 모바일웹으로 먼저.** 위 부품(비전 LLM·기상청·R2·세그멘테이션)은 전부 웹에서도 붙는다. 습관화(홈 위젯) 단계에서 네이티브로.
