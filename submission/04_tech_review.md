## 0. 한 장 결론

**기술은 전부 구현 가능하다. 오히려 이전 모델(옷 조합형)보다 쉽다** — 옷을 오려내고(배경제거) 합성할 필요가 없어졌기 때문. 핵심 기술은 "구글 렌즈·네이버 스마트렌즈"와 같은 **이미지 유사 검색**이고, 이건 이미 성숙했다.

**따라서 승부처가 이동했다.**

| | 기술 난이도 | 진짜 병목 |
|---|---|---|
| ❌ 예전 걱정 | AI 태깅 품질, 배경제거 | — |
| ✅ 지금 | **낮음** (성숙한 기술 조합) | **① 매칭이 '무드'를 잡는가** · **② 합법 사진창고를 어떻게 채우나** |

> **핵심 문장: 서버비는 병목이 아니다(유저 1만 명에 월 13만 원). 진짜 투자는 큐레이션 라이브러리(~700장, 약 350만 원)다.**

## 1. 아키텍처 — 4가지 원칙

| 원칙 | 내용 | 왜 |
|---|---|---|
| **AP-1 · 두 갈래** | 무거운 로직(질의 선택·유사도 랭킹·다양성·로깅·날씨)은 **서버 경유**. 저장·내 저장룩 조회는 **데이터 계층 직접** | 확장성 + 보안 |
| **AP-2 · AI 격리** ⭐ | 비싼 AI(라이브러리 메타 태깅·임베딩)는 **유저가 오기 전 오프라인 배치**에서만 돈다. **실시간 아침 추천 경로엔 AI 호출이 0** | **AI가 죽어도 추천은 캐시+DB로 산다.** 빠르고 싸다 |
| **AP-3 · 캐시가 방파제** | 날씨(`weather_cache`)·라이브러리 이미지(CDN)가 외부 장애를 흡수 | 기상청이 죽어도 앱은 산다 |
| **AP-4 · SPOF 인지** | 앱을 죽일 수 있는 건 **호스팅 · 데이터 백엔드 · DNS** 3층뿐 | 여기만 모니터링하면 된다 |

**AP-2가 이 아키텍처의 구조적 강점이다.** 아침에 유저가 앱을 열면 서버는 (1) 캐시된 날씨를 읽고 (2) DB에서 벡터 검색을 하고 (3) 템플릿으로 이유 문장을 만든다. **LLM 호출이 한 번도 없다.**

### 시스템 흐름

```
[오프라인 배치 · 유저 없을 때]
  라이선스 사진 → 비전 LLM(메타 태깅) → 임베딩 → library_looks 적재
                                                      │
[온보딩 · 1회]                                         │
  퀴즈 3문항 → taste_vector 산출 → profiles 저장       │
  (선택) 참고사진 → 임베딩 1회 → reference_photos      │
                                                      ▼
[매일 아침 · 실시간 · AI 호출 0]                  ┌─────────────┐
  기상청 API → weather_cache ────────────────→  │ ① 하드필터   │ 날씨 부적합 제외
                                                │ ② 벡터 유사도│ pgvector ANN
  질의(참고사진 or taste_vector) ───────────→   │ ③ MMR 다양성 │ 3장 서로 다르게
                                                │ ④ 이유 템플릿│ 결정론(LLM X)
                                                └──────┬──────┘
                                                       ▼
                                          오늘의 3코디 → 저장 → 캘린더
```

## 2. 기술 스택

| 층 | 선택 | 대체 가능성 |
|---|---|---|
| 프론트 | **Next.js (PWA)** — 모바일웹으로 검증, 습관화 단계에서 네이티브 | ✅ 교체 가능 |
| 호스팅 | **Vercel** | 🔴 SPOF (교체 가능하나 이전 비용) |
| 백엔드·DB | **Supabase** (Postgres + **pgvector** + Auth + Storage) | 🔴 SPOF (lock-in 주의) |
| 벡터 검색 | **pgvector** — Supabase에서 **확장만 켜면 됨. 인프라 추가 0** | ✅ |
| 날씨 | **기상청 공공 API** (단기예보 + 과거관측 ASOS) — 무료 | 🟠 캐시로 완화 |
| AI (오프라인) | **비전 LLM**(메타 태깅) + **이미지 임베딩**(분위기 표현) | 🟡 폴백 존재 |
| 이미지 배포 | **CDN + 썸네일** | 🟠 |

> ⚠️ **임베딩 모델은 아직 미확정.** 기존 문서가 깔고 온 **FashionCLIP은 잠정 후보**이며 **'무드/분위기' 캡처가 미검증**이다. → 착수 전 바이크오프로 확정(§6 스파이크①).
> ⚠️ **교체의 유일한 함정 = 임베딩 모델.** 바꾸면 **라이브러리 전체를 다시 임베딩**해야 한다 → 초기에 신중히 고정한다.

## 3. 추천 엔진 — "랜덤 아님"의 기술적 근거

경쟁 앱의 최대 불만이 *"AI 추천이 그냥 랜덤 같다"* 이다. rainism의 처리 순서는 **고정**이다.

| 단계 | 기술 | 하는 일 |
|---|---|---|
| **① 하드필터** | SQL 메타 사전필터 | 오늘 체감온도 밴드에 안 맞거나, 비 예보인데 비에 부적합한 사진을 **제외** |
| **② 분위기 유사도** | **pgvector 코사인 유사도 (ANN 인덱스)** | 질의(참고사진 임베딩 or `taste_vector`)와 가까운 순으로 랭킹 |
| **③ 다양성** | **MMR** | 상위 후보에서 서로 충분히 다른 **3장** 선택 |
| **④ 이유 문장** | **템플릿(결정론)** — LLM 아님 | 날씨 + 메타 태그로 한 줄 이유 생성 |
| **+ 안전빵** | (판정 방식 미결정) | 3장 중 최소 1장은 안 튀는 것 → 신뢰 절벽 방어 |

**①②는 서버에서 단일 SQL로 처리한다** (메타 사전필터 + pgvector ANN). 앱이 라이브러리를 전부 내려받아 계산하지 않는다.

### 반드시 지킬 품질 규칙
- **동일 비교 공간** — 참고사진·라이브러리·취향 셋 다 **같은 모델로 임베딩**해야 유사도가 의미를 갖는다. (다른 모델을 섞으면 유사도 자체가 무의미해진다)
- **반복 방지** — 최근 노출한 코디는 배제 → "어제와 같은 사진" 방지. **고른 것 7일 · 본 것 2일 제외**(2026-07-14 텀 확정, 03 §7.3). 후보가 마르면 본 것 → 고른 것 순으로 풀되 **강수·온도는 안 푼다.**
- **빈손 방지** — 매칭이 부실해도 "결과 없음"을 띄우지 않는다. 라이선스 자산 내에서 폴백.

## 4. 데이터 모델

### 4개 영역

| 영역 | 무엇을 담나 | 테이블 |
|---|---|---|
| 👤 **사용자·취향** | 누가 · 어떤 취향 · (선택)참고사진 | `profiles` · `reference_photos` |
| 🖼️ **큐레이션 라이브러리** ⭐ | 보여줄 코디 사진 풀 — **코어 자산** | `library_looks` |
| ✨ **추천·저장** | 오늘 보여준 것 · 저장한 것 · 착용 확인 | `recommendations` · `recommendation_items` · `saved_looks` |
| 🌧️ **날씨** | 오늘의 숫자 (캐시) | `weather_cache` |
| 📚 참조 | 날씨 하드필터 규칙 · 태깅 어휘 | `coordi_rules` · `taxonomy` |

**저장 형태 4종:** Postgres 행(구조화) · **pgvector 컬럼**(임베딩) · Storage/CDN(이미지 파일) · jsonb(날씨 스냅샷·룩 구성 아이템).

**필수 필드 하나 강조 — 라이선스 출처.** `library_looks`의 모든 행에 **사진의 라이선스 출처를 기록**한다. 문제가 생긴 소스만 잘라낼 수 있어야 하기 때문이다(§7).

### 성능·비용을 좌우하는 설계 3가지

| # | 설계 | 효과 |
|---|---|---|
| 1 | **격자별 후보풀 1회 materialize** — 같은 지역·같은 날이면 하드필터 결과가 동일. 유저마다 재계산하지 않는다 | 사용자가 늘 때 **서버 비용을 가장 크게 좌우** |
| 2 | **이미지 CDN + 썸네일** — 라이브러리 이미지는 전 유저가 공유하는 정적 자산 → 캐시율 최고 | egress 비용이 거의 0으로 |
| 3 | **이유는 템플릿, LLM 아님** — "랜덤 아님"은 하드필터+유사도에서 이미 나온다. 이유 문장에 LLM을 쓸 이유가 없다 | 지연·비용 0, **재현 가능** |

## 6. 라이브러리 소싱 — 최대 리스크 ②

**질문: 합법 코디 사진을 어디서, 몇 장, 얼마에 구하나?**

### 몇 장? — 커버리지 매트릭스

- 상황(날씨) 셀: 서울 여름 92일 실제 분포 기준. **여름의 45%(41일)가 비 오는 날**이고 그 절반이 장마 한 달에 집중.
- 취향 셀: **무드 4 × TPO 4 = 16셀** (색은 하드 셀이 아니라 유사도가 반영하는 소프트 속성)

| 단계 | 계산 | 목표 |
|---|---|---|
| **스파이크용**(내부, 비출시) | 임베딩 바이크오프 검증 | **150~200장** |
| **검증 출시** | 우선 상황 5셀(여름의 88%) × 16 취향셀 × 8장 = 640 + 얇은 커버 ~100 | **~700장** |
| 시즌 완성(검증 성공 후) | 전 셀 × 15장 | ~1,500장+ |

> **왜 셀당 최소가 필요한가:** 장마처럼 같은 상황이 2주 이어지면 유저는 같은 셀에서 3장씩 반복해서 본다. **재고가 얇으면 "어제랑 같은 사진"이 뜬다** — 신선함의 병목은 알고리즘이 아니라 **재고량**이다.

### 어디서? — 소싱 옵션 비교

| 옵션 | 합법성 | 장당 비용 | 판정 |
|---|---|---|---|
| **B. 크라우드픽 확장 라이선스** (국내 스톡) | ✅ "플랫폼에서 유저에게 이미지 제공" **명시 허용** | 5,000원 | **🥇 주력** (재고·퀄 스팟체크 필요) |
| **C. 크리에이터 직접 계약** | ✅ 계약서만 제대로 쓰면 가장 깔끔 | 0.5~2만원(협상) | **🥈 시그니처 셀용** — 품질 최고, 한국 감성 |
| A. AI 생성 | ✅ 사용 가능하나… | 50~150원 | **🚫 노출 제외** — 분위기 훼손·"가짜" 신뢰 리스크. **내부 검증 전용** |
| D. 해외 스톡(셔터스톡 등) | ✅ Enhanced 필요 | 9만~13만원 | **❌ 탈락** (700장 = 6천만원+, 한국 데일리룩 없음) |
| E. 어필리에이트 이미지 | ⚠️ 구매 유도 맥락에서만 | 무료 | **❌ 라이브러리 불가** — gap-filler(수익모델) 전용 |
| F. 무료 스톡(Unsplash 등) | ⚠️ "경쟁 서비스 복제" 금지 조항 | 무료 | **스파이크 내부 테스트 전용** |
| G. UGC(유저 업로드) | ✅ 동의 설계 시 | 무료 | **장기** (콜드스타트를 못 풂) |

> **검증 출시 ~700장 · 실사진만 · 약 350만 원.**

## 7. 규제·법 체크

| 시점 | 법 | rainism에서의 의미 |
|---|---|---|
| **상시** | **저작권·초상권** | 라이브러리 사진은 **소유/라이선스만**. 참고 사진은 유저 본인 것. **스크래핑 금지** |
| **상시** | **개인정보보호법(PIPA)** | 참고 사진(얼굴 가능)·위치 = 개인정보 → **수집 동의·목적·보관기간** 필요. 온보딩에 동의 + 처리방침 |
| **2026.7.1** | 전기통신사업법(이미지 필터링 확대) | 유저 업로드 이미지 → **사전 자동 모더레이션 필수** |
| 2026.1 | AI 기본법 | "왜 이 사진을 추천했나" **설명 제공** 방향 → 우리는 이미 "한 줄 이유"가 있음 ✅ |
| 2026.7.7 | 정보통신망법 | 일 활성 100만↑ 시 자율규제. 초기엔 미달 |

### 하드 제약 — 되살리기 금지 🚫

- 🚫 **핀터레스트 직접 연동** — 공개 핀/피드 API가 **없다**(본인 보드만). 스크래핑 = 저작권 침해
- 🚫 **웹·SNS 패션 이미지 스크래핑** — 저작권 + 부정경쟁 + 약관 3중 리스크
- 🚫 **노출 라이브러리에 AI 생성 이미지** — 실사진만(2026-07-10 결정)
- 🚫 **배경제거·의류 세그멘테이션** — 옷을 조각내지 않는다. 원본 통째 매칭
- 🚫 **날씨 다매체 스크래핑** — 기상청 원천 수치만
- 🚫 **추천 이유를 요청마다 LLM 생성** — 결정론 템플릿

## 8. 착수 전 반드시 — "3 스파이크" 🔴

> **설계를 바꿀 수 있는** 항목이라, 확정 전에는 관련 정의를 임의로 못 박지 않는다. 빌드 후 발견하면 재작업이 크다.

| # | 스파이크 | 질문 | 무엇이 걸려 있나 |
|---|---|---|---|
| **①** | **임베딩 바이크오프** ⭐ | 이미지 표현이 **'무드/분위기'** 를 잡는가? (FashionCLIP 가정은 미검증) | **제품의 상한.** 취향 프로필 산출법 + '분위기 표현' 정의 전체 |
| **②** | **라이브러리 커버리지** | 셀별 최소 장수 → 총 목표 규모 | 콜드스타트. 얇으면 "어제와 같은 사진" |
| **③** | **규제 체크** | PIPA(사진·위치 동의/보관) + 2026.7 모더레이션 최소 요건 | 출시 차단 요건 |

**확정 방법(①):** 라이선스/샘플 사진 + 무드 라벨로 후보 표현 방식들을 **사람 평가(top-3 관련성)** 로 비교해 승자 선택.

### 🔬 스파이크① 예비 측정 (2026-07-13) — **경고 신호**

프로토타입에 실제 CLIP(`clip-vit-base-patch32`)을 붙여 **라이브러리 31장으로 1차 측정**했다.

| 지표 | 결과 |
|---|---|
| **최근접 이웃이 같은 무드일 확률** | **43%** |
| 랜덤 기준선(최빈 무드 비율) | **37%** |
| 코사인 유사도 분포 | 0.68 ~ 0.82 — **변별력이 낮음**(값들이 몰려 있음) |

**해석: 기본 CLIP은 '무드'를 거의 못 잡는다.** 43% vs 37%는 우연과 큰 차이가 없다. 특히 *미니멀* 사진을 질의로 넣으면 최상위에 *러블리*가 올라온다.

**단, 결론은 아니다.** 표본이 31장뿐이고, 무드 라벨도 1명이 붙인 것이다. 다음을 반드시 해봐야 한다:
1. **FashionCLIP·SigLIP·Marqo-FashionCLIP** 등 패션 특화 모델과 비교 (기본 CLIP은 *"무엇이 찍혔나"* 용이지 *"어떤 분위기냐"* 용이 아니다)
2. 표본을 **150~200장**으로 늘리고 라벨러를 2명 이상으로
3. 그래도 안 되면 → **임베딩 단독 랭킹을 포기하고 메타태그 필터 + 임베딩 하이브리드**로 설계 변경

**이 측정이 스파이크①이 왜 최우선인지를 그대로 보여준다.** 라이브러리에 350만원을 쓰기 전에 반드시 닫아야 하는 문제다.
