# rainism — 기반 디자인 시스템 선정

> 작성 2026-07-13 · **팔레트 갱신 2026-08-17(블루그레이 → 분홍)** · 근거: [06_design_principles](06_design_principles.md) · [07_information_architecture](07_information_architecture.md) · [03_PRD §10](03_PRD.md)
> 기술 스택(PRD §10): **Next.js(PWA) · Vercel · Supabase(Postgres + pgvector) · 기상청 API** · 모바일웹 · 한 손

---

## 0. 결론

> ### **shadcn/ui + Tailwind — 단, 컴포넌트는 4개만 가져오고 기본 룩은 반드시 갈아엎는다.**

이유는 *"컴포넌트가 많아서"* 가 **아니다.** 정반대다 — **이 앱은 쓸 컴포넌트가 거의 없다.** 그래서 **브랜드가 없고, 소스를 우리가 소유하고, 안 쓰는 걸 안 깔 수 있는** 것을 고른다.

---

## 1. 먼저 — 이 앱은 UI가 거의 없다

디자인 시스템을 고르기 전에, **실제로 뭘 쓰는지** 세어야 한다. 프로토타입의 클래스를 전부 뽑아보면 UI 어휘는 이게 전부다:

> `버튼` · `선택지` · `칩` · `카드` · `토스트` · `진행 점`

나머지는 **전부 이 제품 고유의 사진 UI**다. 정리하면:

### ① 어떤 라이브러리에도 없는 것 — **직접 짠다 (= 이 제품 그 자체)**

| 컴포넌트 | 왜 없나 |
|---|---|
| **코디 카드** (사진 + 이름 + 칩 + 한 줄 이유 + 구성 아이템 + 결정 버튼) | **이게 제품이다.** 어떤 시스템도 안 준다 |
| **무드 사진 2×2 그리드** | 원칙 4의 구현체 |
| **날씨 배지 · 날씨 히어로** | 도메인 고유 |
| **시간별 강수 바** | 도메인 고유 |
| **기록 캘린더 셀** (사진이 배경 + 날씨 이모지) | 일반 캘린더가 아니다 |
| **「아직 안 알려준 날이 N일」 착용 확인** | 도메인 고유 |
| **하단 탭바** | shadcn엔 **없다** (Material엔 있음) |
| **온보딩 진행 점** | 15줄 |

### ② 라이브러리에서 가져올 것 — **딱 4개**

`토스트` · `바텀시트/다이얼로그` · `스켈레톤` · `버튼(베이스)`

### ③ 브라우저가 이미 주는 것 — **아무것도 안 깐다**

`<input type="time">` (알람 시각) · `<input type="file" accept="image/*">` (사진) · `<dialog>`
→ 타임피커·업로더 라이브러리를 **깔지 않는다.**

> **그래서 판정 기준이 바뀐다.** *"컴포넌트가 많은가"* 가 아니라 **"우리 사진 UI를 방해하지 않는가"** 다.

## 2. 후보 비교

| | **shadcn/ui + Tailwind** | **Material Design (MUI/MD3)** | **Ant Design** | **Apple HIG** |
|---|---|---|---|---|
| **정체** | 복붙하는 **컴포넌트 소스** (npm 의존성 아님) | 구글의 **완성된 브랜드 시스템** | 엔터프라이즈 **데스크톱** 시스템 | **가이드라인 문서** (웹 구현체 없음) |
| **원칙 5 「조용한 확신」** | ✅ **브랜드가 없다** → 사진이 주인공 | 🔴 ripple·elevation·FAB — **UI가 자기를 뽐낸다.** 축하하는 톤 | 🔴 엔터프라이즈 톤. 사진 앱과 정반대 | ⚪ 관례 자체는 조용함 |
| **원칙 1 「결정 대행」** | ✅ 안 쓰는 컴포넌트를 **안 깐다** | ⚠️ 풍부한 컨트롤이 오히려 유혹 | 🔴 Table·Form·Transfer… **전부 안 씀** | — |
| **기술 스택 (Next.js/RSC/Vercel)** | ✅ **표준 조합.** 마찰 0 | ⚠️ CSS-in-JS ↔ RSC 마찰 + 번들 큼 | ⚠️ 무겁고 모바일은 antd-mobile 별도 | 🔴 **웹 구현체가 없다** |
| **필요 컴포넌트 보유** | 4개 필요 → **다 있음** | 다 있음 + 안 쓰는 것 수십 개 | 우리가 쓰는 게 **거의 없음** | 없음 |
| **하단 탭바** | ❌ 직접 (15줄) | ✅ 있음 | ⚪ antd-mobile에 있음 | ✅ 관례 정의됨 |
| **AI 코딩 도구 생성 품질** | ✅ **최상** | ⚪ 중간 | ⚪ 중간 | 🔴 해당 없음 |
| **접근성** | ✅ Radix (포커스·키보드 공짜) | ✅ 좋음 | ⚪ 보통 | ✅ 좋음 |
| **판정** | ✅ **채택** | ❌ 브랜드가 너무 세다 | ❌ 용도가 정반대 | ⚪ **참조로만** |

### 탈락 사유 — 짧게

**Material Design.** 기술적으로는 쓸 수 있다. 문제는 **성격**이다. ripple·elevation·FAB·vivid color role은 UI가 **자기 존재를 알리는** 언어인데, 우리 원칙 5는 정반대다 — *"축하 애니메이션·뱃지 없음. 도파민이 아니라 안도."* 게다가 **사진이 주인공**인 앱에서 채도 높은 머티리얼 색은 **사진과 싸운다.** 화면의 90%가 옷 사진인데 UI가 시선을 가져가면 진다.

**Ant Design.** Table·Form·DatePicker·Transfer — 우리가 **하나도 안 쓴다.** 엔터프라이즈 어드민용이다. 모바일은 antd-mobile로 갈아타야 하는데 그러면 shadcn 대비 이점이 0이다.

**Apple HIG.** 이건 **디자인 시스템이 아니라 문서**다. 구현체(SwiftUI/UIKit)는 웹에서 못 쓴다. 다만 우리 타깃(20대 여성)의 iPhone 비중이 높으니 **관례는 훔친다** — safe-area 여백, 하단 탭바 배치, 바텀시트 제스처, **최소 터치 타깃 44px**. **채택이 아니라 참조.**

## 3. 🔴 shadcn을 고를 때의 진짜 함정

> **shadcn 기본값을 그대로 쓰면, 우리가 피하려던 바로 그것을 UI가 만들어낸다.**

shadcn의 디폴트 룩 — **회색 카드 + `rounded-lg` + 얇은 보더 + Inter 폰트** — 는 지금 **"AI가 만든 앱"의 시그니처**다. 그런데 우리 하드 제약(RG-5)이 뭐였나:

> *"유저에게 보이는 코디 사진에 AI 생성 이미지를 쓰지 않는다 — **'가짜/광고' 신뢰 리스크** 때문."*

**실사진을 어렵게 사놓고(350만원), UI가 "AI가 찍어낸 앱" 같으면 그 돈이 새어나간다.** 사진의 진정성과 UI의 진정성은 한 몸이다.

**→ shadcn은 "가져다 쓰는 스킨"이 아니라 "우리 토큰을 얹을 뼈대"로만 쓴다.** 소스를 복붙해서 **우리가 소유**하는 게 shadcn의 방식이고, 그게 정확히 이걸 가능하게 한다.

### 반드시 갈아끼울 3가지

| # | shadcn 기본 | rainism | 왜 |
|---|---|---|---|
| **1** | Inter (한글은 시스템 폰트로 폴백) | **Pretendard Variable** (서브셋) | 화면이 **전부 한글**이다. 폴백은 선택이 아니라 사고 |
| **2** | 버튼 높이 `h-9` (**36px**) | **최소 48px** | 아침·한 손·짧은 응시(NFR-3). HIG 44 / MD 48 |
| **3** | 중립 회색 (`slate`/`zinc`) | **프로토타입 토큰** (아래) | 순수 회색은 "안 고른 색"이다. **로고에서 나온 분홍** — 스플래시와 본문이 같은 앱으로 보여야 한다 *(2026-08-17 블루그레이에서 교체)* |

## 4. 토큰은 이미 있다 — 프로토타입에서 그대로 가져온다

프로토타입이 이미 쓰고 있는 팔레트가 **원칙의 구현체**다. 새로 만들 필요가 없다.

> ⚠️ **2026-08-17에 블루그레이 → 분홍으로 갈아탔다.** 아래는 지금 프로토타입이 실제로 쓰는 값이다. (이전 값은 이 절 맨 아래에 남겨뒀다.)

```css
--ink:    #4a2338   /* 본문 — 검정이 아닌 짙은 자주 */
--sub:    #b0688c   /* 보조 */
--line:   #f6dde8   /* 경계 */
--accent: #ff6b9d   /* 강조 — 분홍 */
--accent2:#ffe0ed   /* 강조 배경(선택 표시·정보 박스) */
--bg:     #fdf0f6   /* 화면 바탕 */
--rain:   #e0568a   /* 비 (도메인 색) */
--safe:   #8bb38b   /* "무난해요" (의미 색) — 그대로 둔다 */
--heart:  #e0567a   /* 결정됨 */
```

화면 바탕은 단색이 아니라 **위에서 아래로 흐르는 분홍**이다.

```css
background: linear-gradient(180deg, #fff0f6 0%, #fce4f0 40%, #f8d7ea 100%);
```

**카드는 반투명 흰색 + 분홍 테두리**로 띄운다. 분홍 바탕 위에 옅은 분홍 카드를 올리면 배경과 붙어서 안 보인다(실제로 그렇게 됐다가 고쳤다).

```css
background: rgba(255,255,255,.72);
border: 1.5px solid rgba(255,192,203,.45);
box-shadow: 0 2px 10px rgba(255,150,180,.10);
```

→ **Tailwind `theme.extend.colors`로 그대로 옮긴다.**

**의미 색은 강조색과 분리한다.** `--safe`(무난해요) · `--heart`(결정됨)는 **상태**를 나타내는 색이지 브랜드 색이 아니다. 브랜드가 분홍이 되면서 `--heart`가 `--accent`와 붙어 보이므로, **하트는 색이 아니라 아이콘(♡)으로 구분한다.**

### 🔴 갈아타면서 포기한 것 — 숨기지 않는다

이전 팔레트의 근거는 이랬다: *"화면의 90%가 옷 사진이다. 채도 높은 강조색은 사진의 색과 싸운다."* **이 지적은 지금도 맞다.** 분홍은 저채도 블루그레이보다 **사진과 더 싸운다.**

바꾼 이유는 **브랜드**다. 로고(`RAINISM`)가 분홍 풍선 글씨이고, 앱 색이 파랑이면 **첫 화면과 두 번째 화면이 다른 앱처럼 보인다.** 스플래시와 본문이 따로 노는 쪽이 더 큰 손해라고 봤다.

**대신 이렇게 막는다:**
- **강조 분홍(`--accent`)은 누를 것에만.** 버튼·선택 표시·활성 탭. **면적을 넓게 칠하지 않는다.**
- **사진 위에는 분홍을 얹지 않는다.** 코디 카드 안에서 분홍은 테두리와 ♡ 아이콘뿐이다.
- **바탕 분홍은 아주 옅게**(`#fdf0f6`) — 사진보다 밝고 채도가 낮아야 사진이 앞으로 나온다.

⚠️ **아직 확인 못 한 것:** 이 절충이 실제로 통하는지는 **라이브러리 사진 700장**(지금은 39장)에서 다시 봐야 한다. 채도 높은 옷 사진이 많아지면 분홍 바탕이 시끄러워질 수 있다.

<details><summary>이전 팔레트 (2026-08-17 이전 · 참고용)</summary>

```css
--ink:    #2b2f38   /* 본문 — 순수 검정이 아닌, 파랑이 살짝 도는 먹색 */
--sub:    #7b8291
--line:   #e2e6ee
--accent: #6a8fbf   /* 저채도 블루 */
--rain:   #5b7aa8

```

## 5. 채택안 — 실제로 설치할 것

```bash
npx shadcn@latest add button badge skeleton drawer
npm i sonner            # 토스트
npm i vaul              # 바텀시트 (drawer가 이걸 씀)
# 끝. 40여 개 나머지 컴포넌트는 깔지 않는다.
```

| 만들 것 | 어떻게 |
|---|---|
| 코디 카드 · 무드 그리드 · 날씨 배지/히어로 · 강수 바 · 기록 캘린더 · 어제 배너 · 탭바 · 진행 점 | **Tailwind로 직접.** 프로토타입 CSS가 이미 설계도 |
| 토스트 | `sonner` |
| 날짜 상세 | `drawer` (바텀시트 — HIG 관례) |
| 로딩 | `skeleton` (스피너 금지 — 레이아웃이 안 튀어야 함, 07 §4) |
| 알람 시각 · 사진 업로드 | **네이티브 `<input>`.** 라이브러리 안 깜 |

> **캘린더 주의:** shadcn `Calendar`(react-day-picker)를 쓰고 싶어지겠지만, 우리 캘린더는 **셀 배경이 코디 사진**이고 날씨 이모지가 붙는다. 커스터마이즈 비용이 직접 짜는 것보다 크다. **직접 짠다.**

## 6. 결정 요약

| 질문 | 답 |
|---|---|
| **원칙과 맞는가** | ✅ shadcn은 **브랜드가 없다** → 사진이 주인공(원칙 5). 안 쓰는 걸 안 깐다(원칙 1) |
| **기술 스택과 맞는가** | ✅ Next.js + Vercel + Tailwind = **표준 조합.** RSC 마찰 0 |
| **컴포넌트가 있는가** | ⚪ **4개만 필요하고, 그 4개는 있다.** 나머지 9개는 어차피 직접 짠다 — **어떤 시스템을 골라도 마찬가지** |
| **가장 큰 리스크** | 🔴 **shadcn 기본 룩 = "AI가 만든 앱" 시그니처.** 350만원짜리 실사진의 진정성을 UI가 깎는다 → **토큰·폰트·터치타깃 3개를 반드시 갈아끼운다** |

---

*디자인 시스템은 이 제품의 10%다. 나머지 90%는 사진 카드 하나에 달려 있다. 그래서 고르는 기준은 "무엇을 주는가"가 아니라 **"무엇을 방해하지 않는가"** 다.*
